## 第 0 章:先建立一个整体图像(3 分钟读完)

在动手之前,你要先想清楚一件事:**"知识库"这三个字里,其实混着三种完全不同的东西**。新手最容易犯的错,就是把它们当成一个东西,一股脑塞进同一个向量数据库。

打个比方:

- 一部分知识,像**字典**——"instance() 就是 instantiate(),没有二义性"。字典你不需要"检索",你需要"查表",一次比对就该 100% 命中。
- 一部分知识,像**说明书里的经验段落**——"yield 改 await 时,有时候要把代码顺序也调整一下"。这种东西没有标准答案,需要"理解",适合用语义检索。
- 一部分知识,不是"知识库"里的内容,而是**当前正在处理的这个仓库本身**——它的场景树长什么样、这个函数被谁调用了。这个每个仓库都不一样,不能提前塞进知识库,只能现场建、现场用、用完扔。

所以你今天要建的不是"一个 RAG",而是**三层不同的存储**,合起来给 Agent 提供一个统一的检索工具。这是本方案唯一的核心思想,后面所有的选型和时间表都是从这一条推出来的。


| 层              | 存的是什么                                 | 打个比方           | 怎么存         | 要不要 embedding |
| -------------- | ------------------------------------- | -------------- | ----------- | ------------- |
| **A 层:规则字典**   | 官方转换器里那些"改名就完事"的确定性规则                 | 英汉词典           | SQLite 表    | 不需要,直接查       |
| **B 层:经验语料**   | 没法写成表格的、需要理解上下文的迁移知识(协程重排、已知的转换器 bug) | 说明书里的注意事项段落    | 向量数据库       | 需要            |
| **C 层:仓库现场索引** | 当前这个仓库自己的代码结构、场景树、依赖关系                | 你正在装修的这套房子的户型图 | 每个仓库现建的临时索引 | 不需要           |


**你原计划里最大的风险,是想把"官方 issue 全量灌进向量库"当作主力。这是个陷阱**,理由很简单:官方转换器的重命名表(`renames_map_3_to_4.cpp`)和逐版本 API 快照(`extension_api.json`)本身就是**结构化、机器可读**的,你应该"编译"它们变成 A 层字典,而不是当成文章去"检索"。issue 里 95% 是引擎本身的 bug,跟"帮用户迁移一个项目"没关系,一天内你也没时间验证灌进去到底是帮忙还是添乱。**所以 issue 语料从主力降级为"锦上添花",A 层字典才是今天真正要死磕的东西。**

## 第 1 章:回答你的核心疑问——要不要自建知识库?

**结论:必须自建冻结的本地语料,不能直接接网络搜索当检索工具。** 原因不是"网络搜索召回差",而是三个工程上站不住脚的硬伤:

1. **你的评测实验要求语料两次运行完全一致**。你在 Day 6 要交付"加 RAG vs 不加 RAG,同一个模型,提升几个百分点"这张表。如果语料来自实时网络搜索,你今天搜到的结果和明天搜到的不一样,这个对比实验直接不成立——不是"差一点",是"根本没法做"。
2. **网络搜索没有版本锁定**。搜 `AnimatedSprite2D`,搜索引擎大概率把 Godot 4.0 时代的帖子和 4.4 的排在一起,你没法过滤"这条规则只对 4.2 以后有效"。
3. **你在 Day 5 要跑几十个 worker 并发**。每个 worker 都对外发起搜索请求,既慢(1-3秒一次)又贵,还容易被限流——你等于给自己的系统新增了一个不可控的外部依赖和熔断点。

**但网络搜索不是完全没用**,把它降级成一个"最后的退路"就很合理:本地检索如果连续几轮都给不出高置信度的结果,再触发一次 `web_search_fallback`。这样你还能顺手统计一个指标——"网络兜底触发率",这本身就是回答"为什么不直接用网络搜索"这个面试问题的实证数据。

**"不重复造轮子"体现在哪里**:向量数据库、embedding 模型、BM25、混合检索排序算法——这些全部用现成的开源工具(下面选型会给出具体的包名)。你自己要写的,只有"怎么把官方的表编译成规则库"这一段代码,这段确实没有现成工具能替你做。

## 第 2 章:三层知识库分别放什么(对应你问题 2、3)



### A 层:规则字典(今天投入产出比最高的部分,不能省)

**来源和为什么可信**:


| 内容                                               | 从哪来                                                                                                               | 备注                                                     |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 3→4 的类名/函数名/属性名/信号名/枚举/项目设置/主题属性/内置类型/shader 重命名 | Godot 引擎源码里的 `editor/renames_map_3_to_4.cpp`,这是官方转换器实际用的那张表,本身就是分组的数组                                             | 直接解析这个文件,比你自己整理准                                       |
| 4.x 各小版本之间的 API 差异(类被删除、方法参数变了、枚举值变了)            | 用 `godot --dump-extension-api` 导出的 `extension_api.json`,不同版本各导一份,做差异对比(diff)                                      | 这就是你问题2里想要的"4.x 到 4.7 的微重构规则",不需要读一条 issue,直接用差异结果自动生成 |
| 破坏性变更的官方说明(带影响范围标注)                              | godot-docs 仓库里的 `upgrading_to_godot_4.x.rst` 系列文档,官方自己写的逐版本升级指南,而且每一条都标注了"是否二进制兼容""是否源码兼容",还附了对应的 GitHub issue 编号 | 这是结构化表格,不是散文,直接解析表格行                                   |


**几条一定要标注出来的"陷阱规则"**(这些是你面试时最值钱的素材,因为体现了你对系统边界的认知):

- `RectangleShape2D.extents` 改名成 `size` 是**对的**,但数值语义变了(旧的 extents 是半宽半高,新的 size 是全宽全高)——**编译能通过,但物理碰撞体全部错误缩放了一半**。这条一定要打上 `语义有风险` 的标记,并附带警告文字,专门喂给后面的 judge 环节。
- 转换器**不处理** shader 文件的迁移(官方已知的一个缺陷),而且 `--check-only` 这个校验命令本身**也检测不到** shader 里的问题——也就是说,这类错误你的客观验证信号是"看不见"的,必须单独处理或者直接判定为需要人工介入。
- 转换器对 `project.godot` 里的项目设置(比如视口宽高)有遗漏——这条要标"转换器已知缺口"。
- `--check-only` 这个校验命令本身有两个已知的误报(不加载 autoload、不认识插件的单例),会把 Agent 引导去"修一个根本不存在的 bug"。这条不是规则,是"假阳性过滤名单",检索到时直接告诉 Agent"这是误报,别改"。

**没法压缩成一行字典的"语义级重构规则"**(手写补充,这部分虽然不多,但命中率极高,漏了会很痛):

`yield` 改 `await` 常伴随代码顺序调整、Tween 系统整体重构、`KinematicBody.move_and_slide()` 改成 `CharacterBody` 的 `velocity` 属性(这是真实世界里最容易出错、需要改好几行的场景)、旧的字符串式信号连接改成 `Callable` 对象、`setget` 改成标准 getter/setter、`File`/`Directory` 合并成 `FileAccess`/`DirAccess`、`OS` 类被拆分成 `OS`/`Time`/`DisplayServer`/`Engine` 四个类、`@tool`/`@onready`/`@export` 等注解语法变化、插件开发用到的 `EditorPlugin` 虚函数改名(因为你的目标仓库很多是 addon,这条命中率会很高,不要漏)。

### B 层:经验语料(向量检索,量不用大)

把 godot-docs 的升级指南文档、以及经过筛选的高质量 issue/论坛贴放进来。**注意:这里的目标不是"覆盖面广",而是"覆盖那些没法写成规则表的经验"**。切分文档时按官方文档自己的章节标题切,不要用固定长度硬切,否则一条完整的迁移建议可能被切成两半。

### C 层:仓库现场索引(你问题3里说的"codebase 场景树",这块被你的原方案低估了)

这一层不进向量库,是每次处理一个新仓库时**现场建、用完就扔**的轻量索引,靠正则或简单解析就能做,不需要 AST 库(时间紧的情况下正则完全够用):

1. **符号表**:这个仓库里所有的类名/函数名/信号/变量/常量,以及它们在哪个文件哪一行定义。
2. **反向引用**:某个符号被哪些文件调用过——改之前先看看波及范围。
3. **依赖关系图**:靠 `extends` 继承关系和 `preload`/`load` 引用关系连成的图,再加上场景文件里的资源引用边。**这一步很关键**:很多报错其实是"一个根本问题引发的连锁反应",比如一个基类脚本坏了,继承它的十几个文件都会报错。有了依赖图,你就能只修根节点,不去追着一堆"症状性报错"瞎跑。
4. **场景树解析**:`.tscn` 文件本质是类似 INI 的文本格式,解析出节点名/类型/父子关系/挂载的脚本/信号连接——这样 Agent 才能知道"改了这个节点类型,场景里引用它的地方会不会跟着坏"。
5. `project.godot` **解析**:重点是拿到 **autoload(自动加载单例)列表**。前面提到 `--check-only` 会误报"找不到某个标识符",而这个标识符其实是个 autoload——有了这份列表,就能当场识别出这是误报,而不是让 Agent 去瞎改。
6. **资源版本信息**:`.tres`/`.res` 文件头部的格式版本号、`.import` 文件、4.4 版本后新增的 `.uid` 文件。

**为什么这一层比"灌 issue"更值钱**:issue 语料解决的是"我不知道某个 API 怎么改",而 C 层解决的是你在 badcase 分析里列出的两个最常见、最贵的翻车场景——"误判假阳性"和"追着连锁反应瞎改"。这两个问题不解决,规则表再全也没用。

### 统一入口怎么设计

Agent 不需要知道有三层,只暴露给它一个检索工具和几个读取工具:

```
retrieve_migration_rule(错误信息, 目标版本)   ← 内部自动路由到 A 层查表 或 B 层混合检索
grep_symbol(符号名)                          ← C 层,直接查
read_scene_tree(文件路径)                     ← C 层,直接查
is_known_autoload(符号名)                     ← C 层,专门用来戳穿假阳性
```

路由逻辑很简单,不需要模型参与决策:先按符号名去 A 层字典精确查,查到直接返回(置信度 1.0);查不到再去 B 层做混合检索。这样可以避免"让模型自己选该用哪个检索工具"这种多余的失败点。

## 第 3 章:怎么在没有标注数据的情况下做量化评测(对应你问题2里"缺少验证数据集")

这是本方案里最容易被忽略、但其实最省事的一步:**你不需要人工标注,因为 A 层字典本身自带标准答案**。

道理很简单:字典里每一行都是"旧写法 → 新写法"的映射,你完全可以**反向操作**——拿一个已经是 4.x 的健康仓库,用字典把它"退化"回 3.x 的写法,这样你就精确知道每一处改动对应哪条规则,这就是一份完美的验证集,而且可以无限生成。


| 验证集              | 怎么造                                                              | 标准答案哪来的              | 人工成本     |
| ---------------- | ---------------------------------------------------------------- | -------------------- | -------- |
| **测试集1:规则直查**    | 把字典每一行的"新写法"喂给你 Day 1 写好的错误解析器,生成一条**跟真实报错长得一模一样**的错误信息          | 就是这条规则本身             | 0(纯代码生成) |
| **测试集2:文档引用回指**  | 官方升级文档里每条说明后面都附了 issue 编号,拿文档描述当查询                               | 它引用的那篇文档/issue       | 0        |
| **测试集3:仓库级真实场景** | 用第一步"仓库退化"的方法,在真实仓库里造出大量错误,再跑 verify 拿到真实报错(会混着连锁报错和噪音,比测试集1更真实) | 每处改动对应哪条规则,退化时就记录下来了 | 0        |
| **测试集4:难例手标**    | 针对 yield/Tween/move_and_slide/假阳性这些没法写成简单映射的场景,手写 15-20 条        | 人工标                  | 约30分钟    |


**要报的指标**(不用贪多,下面这几个够用):

- **Recall@5**:查询后前5个结果里有没有包对答案。这是最基本、最该优先看的一个数字。
- **分类别拆开报**:普通改名类 vs 语义重构类 vs 假阳性类,分开算,因为它们的难度天差地别,混在一起会掩盖问题。
- **一个你独有的加分指标——"命中了但版本不对"的比例**:比如问的是 4.5 该怎么改,结果检索出了一条只对 4.1 有效的规则。这条指标能体现你对"版本锁定"这个设计目标真正做了验证,而不是嘴上说说。
- **对比实验**:纯关键词检索 vs 纯向量检索 vs 两者混合,三种方式在同一测试集上分别跑一遍,把 Recall@5 列出来对比。**这张对比表,是今天真正要交付的东西**,比"我接了个向量库"有说服力得多。

## 第 4 章:技术选型(每一项只做一次决定,不搞选型对比)

时间紧张时,选型花时间对比是最亏的——工程上「够用、稳定、社区认可」比「新颖」重要得多。以下每一项都直接给结论:


| 组件    | 选定方案                                | 为什么(以及为什么不选别的)                                                                                                                                 |
| ----- | ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 向量数据库 | **LanceDB**                         | 嵌入式,不需要额外起一个数据库服务;自带关键词检索(BM25)和向量检索的混合能力,还内置了结果融合算法。不选 Qdrant/pgvector/Elasticsearch,是因为它们都需要额外部署一个服务进程,在 Day 5 你要跑分布式 worker 时,这就多了一个可能挂掉的东西 |
| 关键词检索 | **LanceDB 自带的全文检索**,另外给"符号名"单独建一个字段 | 不用 SPLADE 这类更"新潮"的稀疏检索方案——那需要额外的模型推理开销,而且它解决的是"用词不一样但意思相近"的问题,你的真实痛点是"版本不一样",这个问题它解决不了                                                         |


> 说明:LanceDB 属于**嵌入式库**,以文件形式跑在你的检索服务进程里,不是一个独立运行的"MCP 服务"。让 Agent 通过 Function Calling(工具调用)访问它是最简单直接的方式;如果你的框架(LangGraph)支持把它包成本地工具,直接包一层薄的检索函数即可,不需要额外起 MCP server。**数据协议保持通用**:检索函数入参用 `{query, target_version, top_k}`,出参统一成 `{id, score, source, kind, version_range, semantic_risk, snippet}` 这样一个通用 JSON 结构——这样以后如果想换成 MCP 或者换一个向量库,上层 Agent 代码完全不用改。
> | Embedding 模型 | `bge-small-en-v1.5`**,通过** `fastembed` **库调用** | 纯 CPU 就能跑,不需要装 GPU 版的深度学习框架,安装快、启动快。效果不够时再升级到 `bge-base`。不用 OpenAI 的在线 embedding 接口,是因为那样每个 worker 又多了一个网络依赖,而且两次调用结果理论上应该一致但没法完全保证,不利于你要做的复现实验 |
> | 结果融合算法 | **RRF(Reciprocal Rank Fusion),用默认参数** | 这个算法不需要调参、鲁棒性好,是混合检索的标准做法。除非后面评测发现向量检索在拖后腿,否则不要去手动调权重浪费时间 |
> | 重排序(rerank) | **今天不做** | 这一步能提升效果但要引入额外的深度学习模型依赖,今天时间不允许。等评测出来如果发现"检索到了但排序靠后"是主要问题,再加,而且优先加"符号精确命中直接提权"这种简单规则,不一定要上模型 |
> | 版本过滤 | **在数据库查询时按** `目标版本` **字段做条件过滤** | 几乎零成本,但价值最高的一个开关,一定要做,而且要做成可以开关对比的,方便写进你的消融实验表格 |

**要调的参数,控制在3个以内**:检索模式(纯关键词 / 纯向量 / 混合)、融合前召回的候选数量(20 或 50)、版本过滤开不开。不要在今天引入更多可调项。

> 上表是 Day 2 当日时间盒。**运行时**的 YAML 调参、可插拔重排槽、0–1 分数与观测 hook 以 [`rag/retriever/`](../rag/retriever/README.md) 为准，不再受「今天不做 rerank」约束。

## 第 5 章:诚实压缩后的时间表(09:00–19:00,含2小时午休,净8小时)

> 相比你原方案,这版砍掉了"全量多版本 API diff""issue 白名单抓取当作必做项""cross-encoder 重排"这几项——它们对最终效果的边际贡献,配不上今天要花的时间。保留的每一项都直接支撑 Day 3 能不能顺利开始跑通。


| 时间              | 做什么                                                                                                                                 | 做完要检查的产出                                                | 卡点没完成怎么办                                                                                     |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------- |

## 第 6 章:如果全天进度都吃紧,兜底方案

**如果连这个都做不完,退到最后一道防线**:一个不需要任何 embedding、纯查表的字典本身就是一个合法的检索方案。这句话可以直接在面试里说出来:"我先验证了'查字典'在符号匹配这件事上比'语义检索'更准,才决定哪部分才真的需要向量数据库"——这个认知比"我接了个向量库"更值钱。

## 第 7 章:三个容易踩的坑,提前知道能省不少时间

1. **规则字典本身不是100%可信的**。前面提过 `RectangleShape2D.extents → size` 这种"改名对了但数值语义变了"的情况——一定要在数据结构里留一个"语义有风险"的标记字段,查到这类规则时要连警告一起返回给 Agent,这个标记后面 judge 环节也用得上。
2. **三个版本号必须对齐,而且要记录下来**:Day 1 用的 Godot 版本、你解析文档时用的 godot-docs 版本、生成 API 差异时用的目标版本——这三者如果不一致,会在你完全没意识到的情况下污染所有后续实验结果。建议把这三个版本号存进一份配置清单里,每次跑评测都带着这份清单一起存档,方便回溯。落地后这张清单就是 `rag/vault/manifest.json`；它和 `manifest.lock.json` 的文件哈希、检索 `cache_key`、`schema_version` 不是同一件事，对照见 [hash_and_manifest.md](hash_and_manifest.md)。
3. **不要把大段原始文档直接丢给 Agent**。检索结果应该是"结构化的规则行在前,少量文字说明在后",控制在一个合理的长度以内,并且要求 Agent 在给出修复方案时必须注明"依据了哪条规则"——这样做除了省 token,还能强制 Agent 有据可依,也方便后面 judge 阶段核对它引用的规则对不对。
