# `untrusted_files` 盲区的交叉验证探索：Prompt 意识 + 主动排查

> **文档性质**：这是一份**探索性提案**，不是已锁定的设计规格。`verifier_filter_scheme.md` §4/§7.3 里定义的 `untrusted_files` 行为（老实标注"不确定"，不主动排查）是**当前生产实现必须遵守的基线**，本文档讨论的是"要不要、能不能在基线之上加一层可选的主动排查手段"，属于 Phase 2 候选项，**没有探针实验支撑之前不能写进 §2 的锁定配置**。
>
> **触发上下文**：源于对 `verifier_filter_scheme.md` 这句话的讨论——
> > `untrusted_files` 非空时，禁止宣称这些文件已证明没有别的编译问题；也不因此把单次 status 改成 HAS_ERRORS。
>
> 用户提出两个方向：① 让 LLM 在 prompt 里意识到这个盲区；② 通过"注释掉 autoload 再单文件编译"做主动交叉验证。本文分别讨论，并指出第②个方向字面上的做法为什么不成立，给出一个基于现有实验结论推导出来的、真正可行的替代方案。

---

## 1. 先复述一次问题本身

`--check-only` 编译一个文件时遇到第一个错误就停，不会继续往下走。如果一个文件长这样：

```gdscript
# uses_autoload.gd
func _ready():
    Config.load()          # 第 1 行：Config 是 autoload 单例，--check-only 不认识它 → 在这里就停了
    some_node.foo_bar()     # 第 2 行：假设这里还有一个真实存在的错误，永远没机会被打出来
```

R2 规则把第 1 行的 `Identifier not found: Config` 删掉（因为它在白名单里，是已确认的假阳性），删完之后这份日志变成"干净"的。但"干净"只代表"我们没看到错误"，不代表"这个文件没有错误"——第 2 行的错误是**假阴性（false negative）**，编译器从来没走到那一行，过滤器不可能凭空发明一个它没见过的错误。

`untrusted_files` 字段就是用来诚实记录这件事的："这个文件的编译在某一行被一个已知假阳性挡住了，挡住的部分我们没检查过"。当前方案对这个盲区的策略是**纯声明式的**：不主动做任何事去消除它，只是把这个不确定性显式地传递给下游（Agent / 人工审查）。这是一个刻意保守的设计——过滤器是纯函数，不起 Godot 子进程，消除这个盲区需要"再跑一次 Godot"，这已经超出了过滤器本身的职责范围（见 `verifier_filter_scheme.md` §1 "过滤器不启动 V3"的原则）。

本文讨论的，就是"如果愿意为了消除这个盲区多付一次 Godot 调用的成本，应该怎么设计"。

---

## 2. 方向一：让 LLM 在 prompt 里意识到这个盲区

这个方向不需要任何新代码，只需要把 `untrusted_files` / `caveats` 里已经存在的信息，原样喂给负责修复的 Agent，并且**用清楚的措辞**告诉它这意味着什么。

### 2.1 为什么这是"低垂的果实"

`FilterResult` / `ProjectFilterView` 里已经有 `untrusted_files` 和 `caveats`（如 `compile_truncated:res://uses_autoload.gd`）这两个字段，数据已经存在，只是目前的方案里没有规定"这些字段最终要以什么样的自然语言喂给 LLM"。这是纯粹的 prompt 工程问题，不涉及过滤器逻辑改动。

### 2.2 具体应该让 LLM 知道什么

建议在组装喂给 Agent 的上下文时，针对 `untrusted_files` 非空的情况，明确写清三件事，缺一不可：

1. **这个文件"当前无报错"不等于"这个文件没问题"**——它的编译在某一行被挡住了，挡住它的那一行已经被判定为噪声删除，但挡住之后的内容完全没被检查过。
2. **触发盲区的原因是什么**（比如"引用了 autoload 单例 Config，而 `--check-only` 从不加载 autoload"），让 LLM 有机会判断"这个文件除了那一行 autoload 调用之外，是否存在其它明显问题"——即使编译器验证不了，LLM 通读代码本身也能发现一部分低级错误（类型不对、拼写错误的方法名等），这是 LLM 能提供、编译器提供不了的一种廉价互补信号。
3. **这不是让 LLM 去"修" `untrusted_files`**——不能把它当成一个新的 reward 目标（否则和 §11 "不要把 warning 当第二档 reward"是同一类错误：LLM 可能会去"修"一个根本不存在的问题，或者反复声称已经修好但过滤器验证不出来，制造新的死循环模式）。这条信息只用于**提高 Agent 对"该文件已验证完成"这个判断的谨慎程度**，不进终止条件、不进重试计数。

### 2.3 落地位置

这属于"外壳/Agent 层的 prompt 组装"，不属于 `verifier_filter_scheme.md` 规定的过滤器纯函数范围。建议在 `merge_command_results` 产出 `ProjectFilterView` 之后，由外壳的 prompt 组装模块读取 `caveats` / `untrusted_files`，翻译成一段固定模板的自然语言提示，而不是要求 LLM 自己去理解 `compile_truncated:res://foo.gd` 这种内部编码。

## 3. 方向二：主动排查——但"注释掉 autoload"字面上不成立

### 3.1 先说清楚字面做法为什么行不通

如果把"注释掉所有 autoload"理解成——把 `project.godot` 里 `[autoload]` 段的声明整段注释掉或删掉——那么 `Config` 这个全局单例**从项目里彻底消失**了。`uses_autoload.gd` 里 `Config.load()` 这一行，`--check-only` 依然完全不认识 `Config` 是什么，报错文案和之前一模一样：

```text
SCRIPT ERROR: Compile Error: Identifier not found: Config
```

编译在同一行停下，什么都没有被"解开"。这个操作没有改变"`Config` 这个标识符对编译器不可见"这个事实，纯粹是搬动了噪声的来源，没有解决盲区。**字面上"注释掉 autoload"不能让编译器往下走，因此不能用来排查第 2 行有没有问题。**

### 3.2 真正需要的是：让 `Config` 变得"可解析"，而不是让它消失

要让编译器跳过第 1 行、走到第 2 行，唯一的办法是让 `Config` 这个标识符**能被解析**——不是删掉引用它的证据，而是给编译器一个它认识的定义。

这里要用到项目自己已经验证过的一个关键事实（两条实验结论拼在一起看，之前没人把它们连起来用）：

| 全局标识符的注册方式 | `--check-only` 认不认 | 证据 |
| --- | --- | --- |
| `[autoload]` 单例（`project.godot` 里的 `Config="*res://config.gd"`） | **永远不认**，WARM 缓存也没用 | N01：`确认 WARM 也消不掉 autoload FP` |
| `class_name` 声明的全局类 | **认**，前提是缓存是 WARM 的（import 过一次） | N03：`T3 import 之后是干净的`，`T6 补 import 后干净` |

也就是说，Godot 4.7.1 的 `--check-only` 有**两条平行的全局标识符注册机制**，`[autoload]` 走的是一条它读不到的通道，`class_name` 走的是另一条它读得到的通道（`global_script_class_cache.cfg`）。这不是巧合的相似，是两个完全独立的子系统——这正是为什么 N01 的假阳性不会随 import 消失，而 N03 的假阳性会。

### 3.3 由此推出的正确排查手段：给单例脚本临时补一个 `class_name`

把 `Config.load()` 解不开的问题，从"走 autoload 通道"换成"走 class_name 通道"：

```gdscript
# 隔离副本里的 res://config.gd（原文件，只加一行）
class_name Config     # 临时追加，原有 autoload 声明不动
extends Node

func load():
    ...
```

**关键点：不是伪造一个假的替身脚本，而是给真实的单例脚本本身临时挂一个 `class_name`。** 这样 `Config.load()` 这行代码在语义上、接口上、类型上都和线上真实情况完全一致——因为解析出来的就是同一份源码，不存在"用一个功能不全的假 stub 去骗过编译器，结果反而制造出新的假阳性（比如 stub 没写 `load` 方法，编译器改报 `Function "load" not found`）"这种风险。

流程大致是：

```text
1. 复制整个 workspace 到一个隔离副本（禁止改动用户原仓，参照 §2.1.4 UID 规范化的先例）
2. 解析 project.godot 的 [autoload] 段，拿到候选单例 key 列表（复用 §8 的 autoload.py）
3. 对目标文件里那条被 R2 删除的 "Identifier not found: X" ，若 X ∈ autoload_keys：
     a. 找到 X 对应的单例脚本路径（同样从 [autoload] 的值里解析）
     b. 检查该脚本是否已存在 class_name（存在则跳过，避免重复声明冲突）
     c. 检查全项目是否已有同名 class_name（存在则跳过，命名冲突，此路不通）
     d. 在该脚本顶部插入一行 `class_name X`
4. 触发一次 V3 import（class_name 变更是 §2.1 触发表里明确要求 import 的场景）
5. 对目标文件重新跑 V2
6. 对比新结果与原始被截断的结果：
     - 若冒出新的 root_cause_errors → 这是真实存在、原来被挡住的错误，回传给 Agent
     - 若仍然 CLEAN → 只能说明"挡住的这一段目前没发现新问题"，注意这仍然不是"证明干净"，
       只是把不确定性从"完全没查过"降级为"查过一层，没查到"——如果文件里还有更深的嵌套依赖
       或第二个 autoload 引用，可能还需要重复本流程
7. 丢弃整个隔离副本，绝不把这个临时 class_name 带回真实结果或用户仓库
```

### 3.4 这个手段不是免费的，要老实列出成本和局限

1. **多一次 V3 import**：这是全方案里最贵的操作，且这里是"因为不确定才多花一次"，如果对每一个 `untrusted_files` 都无条件做一遍，会严重拖慢整体速度。因此这应该设计成**按需触发的可选工具**（比如 Agent 在犹豫"这个文件到底能不能算完成"时主动调用一次），而不是塞进主循环每轮自动跑。
2. **命名冲突**：如果全局已经存在同名 `class_name`，这条路直接走不通，必须老实报告"无法排查"，不能强行覆盖或改名（改名会让接口对不上，产生新的不一致）。
3. **只挪开一层挡板**：如果第 2 行之后还有第二个不同的 autoload 引用（比如 `Config.load()` 后面还有 `EventBus.emit()`），可能要对同一个文件反复做这个流程，每解开一层都要再 import 一次——多层嵌套时成本会线性增长，需要设置一个合理上限。
4. **`class_name` 语义不是 100% 等价于 autoload**：正常情况下这两者的类型检查路径可能有细微差异（比如 autoload 单例在运行时是一个具体的 `Node` 实例，`class_name` 关注的是脚本的静态类型），理论上不能完全排除"通过 class_name 通道看到的类型检查结果，和真实 autoload 场景下的检查结果有细微出入"的可能性——这一点目前只是理论推演，还没有实测验证，见下一节。
5. **这套流程本身还没有被探针实验验证过**：它是从 N01 + N03 两条已confirmed 的结论**逻辑推导**出来的，但"给 autoload 脚本追加 class_name 后，--check-only 是否真的能解开后续代码"这件事本身，目前没有一次实测。在写入任何生产代码之前，应该先补一个新的探针实验（建议编号 N16，或作为 N01/N03 的追加子实验）去验证这个推导是否成立。

### 3.5 一个更简单、风险更低的备选方案：目标行"挖空"法

如果不想承担"补 class_name + 多一次 import"的复杂度和成本，还有一个更直接、完全不涉及 import 的备选思路，值得在同一份文档里一起比较：

在隔离副本里，把触发假阳性的那一整行（`Config.load()`）直接替换成一个语法上无害的占位语句（比如 `pass`，如果在表达式上下文则替换成能通过语法检查的最简表达式），保持缩进不变，然后对该文件重新跑 V2：

- **优点**：不需要 import，不需要碰 `[autoload]` 或 `class_name`，实现简单，成本只是一次 V2；也不存在"class_name 通道语义是否等价于 autoload 通道"这种不确定性，因为它压根不依赖任何全局标识符解析机制。
- **缺点**：这是纯粹的"移走挡路的那一行"，不是"证明那一行调用本身没问题"——如果 `Config.load()` 这一行本身除了"Config 未注册"之外**还带有其它错误**（比如参数个数写错），这个方法会把这条真错误一起挖掉，看不见。而 §3.3 的 class_name 方案因为让 `Config` 变成一个有完整方法签名的真实类型，编译器仍然会对 `Config.load()` 做正常的参数/存在性检查，能覆盖挖空法覆盖不到的这一类问题。
- 两者可以配合使用：挖空法成本低，可以作为"先看看后面还有没有别的行报错"的第一轮快速探测；如果需要确认"被挡住的这一行调用本身参数对不对"，再上 class_name 方案做更严格的检查。

## 4. 回答用户的具体问题：需要用到 autoload 的 parser 吗？

**需要，而且方案里正好已经规划了这一块，可以直接复用，不用重新写。**

`verifier_filter_scheme.md` §8 定义的 `autoload.py`（`parse_autoload_keys`）目前的职责是：给 R2 规则提供白名单 key 集合，判断哪些 `Identifier not found: X` 该被当假阳性删掉。

上面这套主动排查流程，需要的正好是同一份解析结果，而且需求完全重合：

1. **判断候选**：一条被 R2 删除的事件，只有当它的 `symbol` 落在 `autoload_keys` 里，才值得触发深挖流程——这个判断本来就要用到 `parse_autoload_keys` 的输出，不需要新写一遍。
2. **定位脚本路径**：`parse_autoload_keys` 目前的规格（§8）只返回 key 的 frozenset，不保留每个 key 对应的脚本路径（`Config="*res://config.gd"` 里 `=` 右边的部分）。如果要做 §3.3 的 class_name 注入，需要知道 `Config` 对应的脚本文件在哪——**这需要在 `autoload.py` 里补一个次要产出**（比如一个 `dict[str, str]`：key → 脚本 res 路径），而不是重新写一个解析器。§8 现有的正则 `^(?P<key>[A-Za-z_][A-Za-z0-9_]*)\s*=\s*.+$` 已经把整行都匹配到了，只是目前设计只取了 key 那一半，等号右边的路径本来就在同一次匹配里，补出来是很小的改动。

也就是说，**不需要引入新的解析器，只需要在现有 `autoload.py` 的产出里多留一个字段**（从"只给白名单"扩展成"给白名单 + key→脚本路径映射"），这个扩展不影响 R2 规则现有的用法，是纯增量。

## 5. 这一切应该放在系统的哪一层

用 `verifier_filter_scheme.md` §1 的分层语言来说清楚定位：

- **不属于 `filter_verify_output`**：它不是"看一份文本、判断噪声"，它需要主动改文件、主动多起一次 Godot 子进程，是完全不同性质的操作。
- **不属于 `merge_command_results`**：它不是"合并已经跑完的几次命令结果"，它是"决定要不要、且真的去多跑一次命令"。
- **属于外壳的一个新的、可选的诊断工具**，建议暂命名 `deep_probe_untrusted_file(workspace, target_res_path, symbol) -> DeepProbeResult`，性质上和 §2.1.4 的"入队 UID 规范化"是同一类东西：**都是外壳主动发起的、代价明确、只在特定条件下触发一次的辅助校验**，不是过滤器职责，也不是每轮必跑的主流程。

建议这个工具设计成 Agent 可以按需调用的一个动作（类似 `retrieve_migration_rule`、`read_scene_tree` 这类工具），而不是自动挂在主循环上——因为只有 Agent 自己（结合方向一 prompt 里的信息）才知道"这个 `untrusted_files` 值不值得多花一次 import 的成本去深挖"，例如它可能已经从代码通读判断出"第 2 行看起来没问题"，这种情况下不值得再触发深挖。

## 6. 小结：两个方向都值得做，但性质不同

| 方向 | 是否需要新代码 | 是否需要新的探针实验验证 | 成本 | 建议优先级 |
| --- | --- | --- | --- | --- |
| ① Prompt 意识 | 不需要（数据已存在，只是没约定怎么转述） | 不需要 | 几乎零 | **先做**，且应该在 §2 的过滤器完成后立刻补上，否则 `untrusted_files` 这个字段做出来也没人用 |
| ② 主动排查（class_name 注入） | 需要（`autoload.py` 补脚本路径映射 + 新的外壳工具 `deep_probe_untrusted_file`） | **需要**，建议新增探针实验验证"补 class_name 后 --check-only 能否解开后续代码" | 一次额外 V3 import，命名冲突时不可用 | 作为 Phase 2 可选增强，不阻塞当前过滤器主线的交付 |
| ②备选（挖空目标行） | 需要（隔离副本里替换目标行文本 + 重跑 V2） | 建议一起验证，作为对照组 | 一次 V2，无需 import | 可以和 class_name 方案一起在同一组新实验里对比，谁的覆盖面更大、谁的假阴性更少 |

在没有做新实验之前，**不要把方向②写进 `verifier_filter_scheme.md` 的锁定配置**——这是整个项目一贯的原则（先探针实验、后写入规格），`untrusted_files` 保持"老实声明不确定"这个保守行为，仍然是当前唯一被证据支撑的正确做法。
