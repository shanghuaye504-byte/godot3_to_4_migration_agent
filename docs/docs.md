份文档不是快照,是**增量变更记录**(类似 git 的每次 commit diff,而不是每次的完整文件内容)。增量记录设计成"只记录相邻版本之间变了什么",这是**完全正常且必要**的做法——如果每篇都写"4.0 到当前版本的全部差异",4.7 那篇会重复写一遍 4.0→4.1、4.1→4.2……的所有内容,维护成本爆炸。所以官方这么组织没有问题,**问题只在于你不能原样把 7 份文档喂给 agent 去自己拼接**,而是要在你自己的 build 脚本里,提前把这条链拼好。二、具体怎么合并:给每条规则打一个"生效起点版本",然后全部塞进同一张表核心操作只有一个:**解析每一份 rst 文件时,把这份文档里提到的所有变更,都标记上"这个变更是从哪个版本开始生效的"**,然后把 7 份文档解析出来的规则,全部塞进同一张扁平的表里,不保留"这是第几步"这种顺序信息。文件名 → 这份文档记录的变更,起点版本(since_version)标什么 upgrading_to_godot_4.1.rst (4.0→4.1) → since_version = 4.1 upgrading_to_godot_4.2.rst (4.1→4.2) → since_version = 4.2 upgrading_to_godot_4.3.rst (4.2→4.3) → since_version = 4.3 upgrading_to_godot_4.4.rst (4.3→4.4) → since_version = 4.4 upgrading_to_godot_4.5.rst (4.4→4.5) → since_version = 4.5 upgrading_to_godot_4.6.rst (4.5→4.6) → since_version = 4.6 upgrading_to_godot_4.7.rst (4.6→4.7) → since_version = 4.7 **为什么这样标就够了,不需要额外记录"到哪个版本失效"**:因为 API 变更这件事**具有累积性**——某个类在 4.2 被重命名了,只要之后没人把它改回去,那么它在 4.3、4.4、一直到 4.7 都保持着 4.2 时定下的新名字。所以你只需要知道"这条规则从哪个版本开始生效",检索时用你之前已经设计好的那个过滤条件就行:筛选条件:since_version <= target_version 目标版本是 4.7 的话,`since_version` 是 4.1/4.2/…/4.7 的规则全部符合条件,会被一起检索出来,不需要 agent 关心这条规则最初来自哪一篇文档、经过了几次版本跳跃——**这条"7 步拼接"的工作,在 build 阶段跑一次脚本就永久完成了,agent 运行时看到的永远是一张已经拍平的表**。三、需要额外处理的一个边界情况:同一个符号被改了不止一次这是这种"链式增量文档"特有的坑,`extension_api.json` 直接 diff 首尾快照不会遇到,但解析这 7 份文档时会遇到:**某个方法可能在 4.2 被改了一次名字,又在 4.5 版本习惯写法的老项目,旧记录依然有参考价值。这里唯一要注意的是**给检索结果排序时,同一个符号命中多条规则要按 since_version 降序排在前面**,别让一条早就过时的规则排到了最新规则前面误导 agent。四、一个能替你省时间的优化:不用 7 份全解析,只解析到你的目标版本为止你 Day1 锁定的目标版本是 4.7.1,所以确实需要 4.1 到 4.7 这全部 7 份(因为它们覆盖的正是 4.0→4.7 这条完整链路)。但**这条经验值得记下来,因为它会影响你以后要是换目标版本该怎么做**:如果哪天目标版本变成 4.4,你只需要解析 4 份(`4.1.rst`、`4.2.rst`、`4.3.rst`、`4.4.rst`),`4.5.rst`、`4.6.rst`、`4.7.rst` 这三份完全不用碰——**解析范围永远是"4.0
