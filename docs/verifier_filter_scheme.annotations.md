## 开头的三行引用块

那三行（文档性质 / 证据入口 / 范围）本质上是在划**责任边界**：

- 「文档性质」在说：这不是一份「建议」，是可以直接翻译成代码的规格书，所有结论都有实测支撑，不是拍脑袋写的。
- 「证据入口」在说：如果你怀疑某条规则是不是编的，去 `reports/README.md` 和 `artifacts/` 里能找到原始 stderr 核实，本文档不是唯一真相源，探针日志才是。
- 「范围」在说：这份文档**只管「怎么把 Godot 的输出变干净」**，不管「怎么起 Godot 进程、怎么杀超时进程、什么时候该重新 import」。后面这些属于「外壳」（runner），文档里反复出现「外壳做什么」就是在划这条线。这条线很重要，因为如果不划清楚，实现的人会把「解析规则」和「进程管理」揉成一个大函数，测试起来就必须真的起一个 Godot 进程，会很慢很脆弱。

## 0. 背景：为什么必须过滤

这一节是「问题陈述」，五条对应五类探针实验（N08/N01+N02/N04/N05/N03+N06+N07）。读这节时注意一个隐藏的逻辑：**每一条「噪声」背后都有一个「如果不处理会怎样」的故事**，这个故事比规则本身更重要，因为它决定了规则的边界在哪里。

举例：第 2 条说 autoload 会假阳性，但故事不是「所以要把这类报错都删掉」，而是「Agent 会去改一段本来正确的代码」——这决定了后面 R2 规则必须非常精确地只删一种文案，多删一点都可能把真错误也吃掉。

最后一句「一句话总结」值得多读一遍：**过滤器不是为了让报错变少，是为了让报错变得可信**。这两者听起来像，但设计取向完全不同——前者会倾向于「宁可漏报也别多报」，后者要求「漏报和误报都要显式声明，不能装作不存在」。方案里大量出现的 `untrusted_files`、`caveats`、`shader_not_checked` 都是为了服务后者。

## 1. 过滤器在整条 verifier 里的位置

### 那张流程图

这张图容易被误读成「一次 verify 调用的完整时序」，其实它是**跨越很多轮 Agent 迭代的宏观流程**。关键是要分清三个时间尺度：

1. **入队**：一个仓库被拿来做迁移，只发生一次。
2. **每轮**：Agent 打一个 patch 就跑一次这整套（V1→V2→...），发生 N 次。
3. **收尾门**：只在「看起来已经改完了」那一刻发生一次，用来查平时不查的 shader/UID。

图里从「入队一次」到「下游」中间那一大段（触发/采集/收尾）其实是**同一段逻辑，会被反复调用很多次**，只是每次触发条件不同。如果你在实现 runner 时把这张图理解成线性一次性流程，会漏掉「每轮都要重新判断要不要 import」这件事——这正是这份文档最初要纠正的问题（详见 §2.1 的注解）。

### `filter_verify_output` 和 `merge_command_results` 两个函数

这里刻意拆成两个函数，而不是一个大函数，原因是**它们处理的输入形状完全不同**：前者只看「一份 stdout/stderr」，是无状态的纯文本处理；后者要看「多次调用的结果集合」（一次 V1 + 若干次 V2），需要跨调用记忆。如果硬塞成一个函数，测试第一个函数时就不得不假装自己知道「后续会不会再跑 V2」，这在单元测试里是个噩梦——你无法用一份 stderr 文本测出「这是不是最后一次调用」。

拆开之后，第一个函数极其好测（喂文本，断言结构化输出），第二个函数测的是「合并逻辑对不对」，两者互不干扰。这也是为什么原方案在审核后专门把 R8（原来放在流水线里的 pointer 处理规则）挪出来，单独变成 `merge_command_results`——它天生不属于「处理一份文本」这件事。

### 「过滤器不启动 V3」这句话

这句话看起来只是分工声明，但它背后是一条更深的设计原则：**判断「要不要多跑一次 Godot」是有成本的决策（几秒到几分钟），不应该混进「怎么理解已经拿到的文本」这件事里**。把两者分开之后，「过滤规则错了」和「什么时候该重新 import」变成两个可以独立调试、独立测试、独立改动的问题。如果哪天 import 策略改了（比如发现某个触发条件其实没必要），完全不需要碰过滤器的代码。

## 2. 已锁定、实现时不得改口的配置

### 这一节存在的意义

这份 YAML 本质上是**探针实验最终产出的「配置快照」**——第一阶段做了 9 组实验（N01-N09）加 N15，每一组实验都是在回答一个「这里该怎么设」的问题，答案就沉淀成这里的一行配置。

比如 `require_warm_cache: true` 这一行背后是 N03 整整一张实验卡片（冷缓存下 `class_name` 会假报错，import 一次后就好了）。`shader_channel: V3_on_trigger_or_final_gate` 背后是 N07（shader 错误在 V1/V2 完全看不见，只有 import 阶段能看见）。

**为什么要把这些做成「不得改口的常量」而不是「运行时可调参数」？** 因为这些结论都是针对 Godot `4.7.1.stable.official.a13da4feb` 这个具体二进制实测出来的行为特征，不是设计选择，而是「这个版本的引擎就是这么工作的」。如果换了 Godot 版本，这些值可能全部失效，需要重新跑一遍探针实验，而不是「调一下参数」。把它们写成常量，是在提醒实现者：**别凭直觉改这些值，改之前先看有没有新的实测支撑**。

### 四个配置块分别对应什么

- `verifier.*`：verify 这件事本身的性质判断（怎么算成功、要不要暖缓存、能不能用 `--debug`）。
- `noise_filters.*`：具体每一类噪声怎么处理，是本方案 §7 规则的「配置化摘要」，方便一眼看清全貌，不用翻十几个小节。
- `retry.*`：给熔断/重试计数器的开关——决定 Agent 卷了很多轮还没修好时，「症状」和「假阳性」是不是也算作「又失败了一次」。如果算，级联错误会让熔断器在还没真正陷入死循环时就误触发。
- `import_policy.*`：懒启动触发表的配置化摘要，详细逻辑在 §2.1。

### 那句「不是每次 V1/V2 前先跑一遍 V3」

这是从上一轮审核里补进来的强调句，专门纠正一个容易产生的误解：`require_warm_cache: true` 听起来像是「每次校验前都确保缓存是热的」，读者很容易联想成「每次都 import 一下确保安全」。但它真正的含义是一个**一次性的不变量检查**：只要 `global_script_class_cache.cfg` 这个文件存在，就认为缓存是热的，不用管它到底新不新——「新不新」交给 §2.1 的触发表去判断。

## 2.1 外壳：import 懒启动

这一整节是**为了回应一个非常朴素但容易被忽视的工程问题**：import 很慢，如果每次 Agent 改一行代码就重新 import 一次，迭代速度会被拖垮。但另一方面，完全不 import 又会漏掉一整类错误（shader、UID、class_name 缓存）。这一节就是在这两个极端之间找一条可执行的中间路线。

### 「三个概念，禁止合并」这张表

这是全篇最容易读混的一块，值得专门说清楚三者的差别：

- **缓存不变量**：回答「这个工作区现在能不能正常跑 V1/V2」，是个二元判断（能/不能），检测方法很廉价（看一个文件是否存在）。
- **本轮触发器**：回答「这次改动会不会让缓存过时」，是个针对当前 diff 的判断，每轮都要重新算一次。
- **收尾门**：回答「我们是不是该看看那些平时不看的角落了」，只在「看起来快完工」时才问一次。

三者最容易被合并的地方是：有人会把「触发器判定为不需要 import」和「收尾门判定为需要 import」混成同一次判断，结果就是要么每轮都多跑一次 import（浪费），要么永远不触发收尾门（漏检 shader）。表格里特意用「不做什么」这一列去堵住这种合并倾向。

### 触发表为什么长这样

触发表里的每一行几乎都能对应到某个具体探针实验（N03/N06/N07），这不是巧合——**这张表本质上是把「实验证明会假阳性/假阴性的场景」逐条列出来，变成可执行的检测规则**。表格设计上刻意强调「只对本轮 diff 做静态检查，不要起 Godot 问」，原因是：起 Godot 本身就是要避免的高成本操作，如果为了「判断是否要 import」还得先跑一次 Godot，那这个判断本身就失去意义了。

细节上有一处刻意收紧的地方：`class_name` 检测用 `^[+-]class_name\s` 这种行首锚点正则，而不是简单的子串搜索。这是为了避免注释里写了一句「# TODO: 加 class_name」这种情况被误判成真的改了 `class_name` 声明，导致不必要的 import。这种「宁可保守触发也不要精确匹配漏检」和「别把无关内容误判成触发条件」两种诉求，是在写检测规则时反复要权衡的东西，值得在实现时留意。

### 判定伪代码里的 `phase` 参数

`should_run_v3` 函数按 `phase`（入队/迭代/收尾）分三支，这不是随意的代码组织，而是在强调**同一个「要不要 import」的问题，在三个阶段的判断标准完全不同**：入队阶段只看缓存是否存在；迭代阶段看本轮 diff；收尾阶段看整个项目的完成状态。如果把三者的判断逻辑糅合成一套规则，很容易在某个阶段用错了别的阶段的判断标准。

### 「V1 必须可重复」这条

这条是从审核里补进来的、容易被漏掉的一环：Godot 的哨兵脚本如果自己先解析失败（比如 preload 了一个语法错误的文件），会导致 V1 提前中断，后面本该报出来的错误（比如更深层的 autoload 问题）根本不会出现在这次 V1 日志里。所以单纯「跑一次 V1，处理完 pointer 指向的文件，就此收工」是不够的——**必须把「修完当前这批 pointer」和「再跑一次 V1 看看还有没有新的」变成一个循环**，直到不再有新的 pointer 冒出来，或者达到一个安全上限（比如 8 轮）为止。这个上限的存在也提醒了一件事：这个循环理论上有可能不收敛（比如级联错误特别深），必须有兜底退出条件，不能无限跑下去。

## 3. 实现顺序

这份表格本质上是**给实现者的一张任务清单**，但排列顺序不是随意的，而是按照「依赖关系」从底往上排：`models.py` 先行是因为后面所有模块都要用这些数据结构；`parse.py` 在 `signature.py` 之前是因为要先有解析出来的事件才能算签名；`rules/*.py` 要等 `autoload.py` 先行是因为 R2 规则依赖白名单。

这张表隐含的一条原则是：**每一步都能独立写单元测试，不需要等到最后才能验证**。这是为什么文档反复强调「不依赖 Godot 二进制」——如果一开始就把解析、签名、过滤规则和真实子进程调用绑死，测试速度会很慢，而且每次改一行正则都要重新起 Godot 验证，非常低效。按这个顺序实现，前 7 步全部可以在几毫秒内跑完全部测试。

## 4. 数据模型

### 为什么要分 `RawEvent` 和 `ClassifiedEvent` 两层

这是一个「关注点分离」的设计：`RawEvent` 只负责「把一段文本正确地切成结构化字段」，不做任何是非判断；`ClassifiedEvent` 在此基础上加上「这条事件属于哪一类、该怎么处理」的判断结果。如果不分层，会把「解析对不对」和「过滤对不对」两种完全不同性质的 bug 混在一起调试——比如一条事件被错误地删除了，你需要先确认是解析阶段就抽错了字段，还是分类阶段判断错了角色，两层分开之后这个排查过程会快很多。

### `res_path` 和 `target_res_path` 为什么要分成两个字段

这是审核阶段发现的一个关键陷阱，值得多解释几句。Godot 报错的典型形态是：

```text
Could not preload resource script "res://root_bad.gd"
at: GDScript::reload (res://dep_1.gd:3)
```

这条报错的意思是「`dep_1.gd` 这个文件试图加载 `root_bad.gd`，但 `root_bad.gd` 本身有问题」。如果只用一个字段去装「路径」，写代码的人很容易顺手从离得最近的 `at:` 行去抽路径（也就是 `dep_1.gd`），因为这是最显眼的、格式最规整的一段。但真正需要修的、需要再跑一次 V2 去看具体错误的，是 `root_bad.gd`——藏在 message 文本里，格式不那么统一。

如果这个字段用错了，后果是：Agent 会对 `dep_1.gd` 反复跑 V2，但 `dep_1.gd` 本身没有语法错误（它只是引用了一个坏文件），于是 V2 永远报不出具体错误，Agent 就会在这个文件上打转，永远修不到真正坏掉的 `root_bad.gd`。这是那种「代码能跑、测试也能过基本场景、但在这个特定场景下逻辑整个错位」的 bug，靠人读代码很难一眼看出来，所以专门拆成两个字段、并在多处（数据模型、解析规则、测试用例、完成定义）反复强调，就是为了让这个区分「烧」进类型系统里，而不是靠命名约定或者代码注释去提醒。

### 为什么 `ClassifiedEvent` 要设成 `frozen=True`，又要用 `replace`

设成不可变（frozen）是为了防止规则之间产生「谁改了这个字段」的追踪困难——如果事件对象是可变的，七八条规则依次跑过去，最后发现某个事件的 `role` 不对，你需要一条条排查是哪条规则改的。用 `replace()` 强制「改一个字段就产生一个新对象」，配合流水线「每一步的输出就是下一步的输入」这个结构，出错时只需要打印每一步之间的中间状态就能定位是哪一步改错的，不需要猜。

这也解释了为什么流水线的示意图要写成 `parse → classify → R1 → R2 → ... → 组装 FilterResult` 这种链式箭头——每一步都是「拿上一步的事件集合，产出一份新的事件集合」，不是「原地修改」。

### `FilterResult` 为什么不包含 `INFRA_FAILURE`

这也是一个从审核中纠正过来的点。`INFRA_FAILURE`（超时、进程被 signal 杀死）这类问题，根本没有 stdout/stderr 可以解析——进程可能连输出都没产生就被杀掉了。如果把这个状态塞进 `FilterResult`，会让这个类型看起来「既能装文本解析的结果，又能装进程管理的结果」，两种完全不同来源的信息混在一个字段里，调用者每次读 `status` 字段时都要多想一层「这次的 CLEAN/HAS_ERRORS 是不是真的经过了过滤器，还是外壳自己塞进来的」。拆开之后，`FilterResult` 永远只表示「这份文本被过滤器处理过之后的结果」，`INFRA_FAILURE` 是外壳在**根本没调用过滤器**的情况下就直接下的判断，语义边界很清楚。

### 「单次 vs 项目级」为什么要反复强调

这是全篇除了 pointer 字段拆分之外最重要的一处纠偏。`FilterResult.status == CLEAN` 只能回答「这一份日志里有没有根因」，不能回答「这个项目改完了没有」。样例 F 就是个具体例子：V2 检查 `dep_1.gd` 这个文件，结果是 CLEAN（这个文件本身没有语法错误），但项目远没有修完，因为它引用的 `root_bad.gd` 还坏着，而这条信息以 pointer 的形式挂在 V1 的结果里，不在这次 V2 的结果里。

如果实现者图省事，看到「各个命令的 `status` 都是 CLEAN」就直接判定「这个仓库已经迁移完成」，会导致大量「看起来干净、实际上只是没检查到」的假阴性放行。这也是为什么方案里专门定义了「项目级完成」的判定条件（根因为空 **且** 无未消化的 pointer **且** 已经有一次收尾 V3），并且明确说「不要把单次 `passed` 用在项目级」。

## 5. 解析器

### 为什么行语法要严格限定成「一行前缀 + 一行 continuation」

Godot 的报错输出格式很规整，但正是因为这种规整性，如果解析规则写得太宽松（比如「只要看到 `ERROR:` 就算一条事件，后面随便再拿一行当补充信息」），遇到探针没见过的输出形态时会悄悄解析错，而且不会报错——你会得到一个「看起来正常但字段全错」的结果，比直接崩溃更难发现。所以方案要求严格按 4.7.1 实测的具体格式写正则，「不要放宽到任意 ERROR」这句提醒就是在防止这种隐性错误。

### 匹配优先级为什么要分四级（`AT_SCRIPT` → `AT_ENGINE` → `AT_SHADER` → `AT_GENERIC`）

因为同一个「at: 函数名 (路径)」的语法外壳，根据路径内容的不同，含义完全不一样：路径是 `res://xxx.gd:行号` 说明这是指向项目脚本；路径是 `xxx.cpp:行号` 说明这是指向引擎内部源码（也就是「症状」，不是「根因」）；路径是 `(null) (:行号)` 是 shader 特有的格式。用逐级尝试、优先级从最具体到最通用排列的方式，是为了保证「更精确的模式先被尝试」，避免用一个太宽泛的正则不小心吞掉了本该被更精确模式捕获的内容。

### 5.2 表格怎么读

这张表是整份文档里信息密度最高的一张，建议这么读：**先看最右边一列（角色），再回头看中间两列（怎么从文本里抽取字段），最左边的正则留到真正写代码时再抠细节**。角色这一列决定了这条事件之后会被怎么对待——`protected` 意味着后面所有规则都不能碰它；`pointer` 意味着它的价值在于指向另一个需要检查的文件，而不是它本身的内容；`symptom` 意味着它对 Agent 有参考价值但不该被当成任务本身。

值得特别留意表格最后一句「未匹配的 `ERROR:` 默认为 `engine_error`/`root_cause`，宁可不滤，不可默删」——这是一条兜底原则：遇到探针没见过的新文案，宁可让它当作根因进入 reward（可能是噪声，Agent 花点时间才发现是误报），也不要让它被悄悄吞掉（真错误被藏起来，Agent 永远看不到）。这是整份方案「宁可误报，不可漏报」的价值取向在解析层面的体现。

### 5.3 的十份「黄金原文」是什么

这十份不是随手编的示例，是**直接从探针实验落盘的真实 stderr 里逐字拷贝**的。之所以要求逐字拷贝、不许「参考着写一份类似的」，是因为 Godot 输出里的空格数量、冒号位置、大小写这些细节都是靠真实观察确定的，人凭记忆重写很容易在无关紧要的地方写错，而这些「无关紧要的地方」恰好是正则表达式最容易失配的地方。这十份原文覆盖了十种关键场景（假阳性、真冲突、级联放大、真错误、pointer、多级依赖、冷缓存假阳性、UID 簇、shader），基本上就是这份过滤器所有分支逻辑的验收标准——如果实现完之后这十份都能按预期分类，说明核心逻辑基本站得住。

## 6. 两级 signature

### 为什么要两级，而不是一级

这是整份方案里最容易被问「为什么这么麻烦」的设计，值得展开讲讲。两级签名服务两个完全不同的目的：

- `local_signature` 保留了路径和符号名，所以「`main.gd` 里找不到 `Config`」和「`uses_autoload.gd` 里找不到 `Config`」是两个不同的签名——这是必要的，因为它们确实是两个不同的问题（不同文件），Agent 需要分别知道。这个签名用来做「同一个错误有没有在下一轮消失」的判断（也就是重试计数、震荡检测）。
- `noise_signature` 把路径和符号名都抹掉了，只留下「消息长什么样」这个模板。它原本是探针实验期用来做「背景噪声」减法的工具——把 CleanControl（干净项目）上天然出现的噪声模板记下来，其他项目上如果出现同模板的行，先怀疑是噪声。

两级刻意不让互相替代，是因为它们在粒度上是矛盾的：想要精确定位到「哪个文件的哪个问题」就必须保留路径符号（这样 `noise_signature` 就做不到「同类噪声一次性识别」）；想要「一眼识别出这是不是已知的噪声模式」就必须抹掉路径符号（这样 `local_signature` 就做不到「区分不同文件的同类问题」）。文档里特意举了「`Identifier not found: Config` 和 `Identifier not found: SomeMissingClass` 会被 `noise_signature` 折成同一个模板」这个例子，就是在提醒：**千万不要图省事只维护一套签名，用 `noise_signature` 去做生产环境的实际过滤决策**，那样会把「Config 是已知白名单里的假阳性」和「SomeMissingClass 是一个真正缺失的类」混为一谈，误删真错误。

### 为什么行号要被排除在签名之外

这条的原因很直白：Agent 打的每一个 patch 都可能挪动代码行数（加一行、删一行），如果签名里包含行号，同一个逻辑错误在 patch 前后会被认成两个不同的错误——「震荡检测」（判断 Agent 是不是在原地打转、来回改同一个问题）会因此完全失效，因为它永远看不到「同一个错误又出现了」，只会看到「一个新错误出现了，一个旧错误消失了」。但行号本身对 LLM 判断具体改哪一行是有用信息，所以它没有被彻底丢弃，而是单独存进 `line_in_project` 字段，只是不参与身份判断。

## 7. 过滤流水线

### 为什么规则的执行顺序不能打乱

这条流水线里每一条规则都在假设「前面几条已经处理过了」，顺序错了会产生连锁反应。举几个具体的依赖关系：

- `protected` 标记必须在 R2（autoload 过滤）之前打好，否则 R2 有可能误删一条本该受保护的 `Identifier "X" not declared` 语句（虽然 R2 的匹配条件已经写得很精确，但「先保护、后处理」是双重保险，防止未来有人给 R2 加新条件时不小心放宽了匹配范围）。
- R1（哨兵人造边）要在 R2 之前，因为哨兵自己产生的「compile error」和「Failed to load script」很容易被误认成需要处理的内容，必须先把这些哨兵专属的噪声挑出来，剩下的才是「真实项目里的事件」。
- R3、R4（症状/包装行处理）依赖前面规则先把「谁是被删除的假阳性」定下来，因为 R4 的「升级例外」逻辑（§7.5 里那条窄例外）需要知道「这个包装行对应的 SCRIPT ERROR 是不是被删掉了，还是从来就没出现过」——这个判断顺序错了，整条升级逻辑就会失真。

「后一条规则看到的是前一条 `replace` 过的事件」这句话，配合 §4 里 frozen+replace 的设计，其实是在暗示一种编程模型：**把这条流水线想象成一条流水线上的多道工序，每道工序拿到的是前一道工序处理完的半成品，不是原材料**。理解了这一点，调试的时候只需要在每道工序之间打印一下事件集合的快照，就能定位到底哪一步出了问题。

### 7.1 保护名单为什么单独成一节，且强调「永远不得改为」

这一节表面上是四条规则，但本质上是在给整个过滤器设一道「安全阀」。前面所有其他规则（R1-R7）在设计时都可能有考虑不周的边界情况，保护名单的作用是：**即使某条规则因为实现 bug 误伤了保护名单里的内容，也应该有一层兜底检查把它拦下来**。工程实践上，这种做法通常会配合一条断言（assertion）——如果流水线跑完之后，发现某个原本打了 `protected` 标记的事件的 `role` 变成了别的东西，应该在测试里直接报错，而不是让这个 bug 悄悄溜过去。

### 7.2-7.7 各条规则的共同结构

如果你把 R1 到 R6 这几条规则并排读一下，会发现它们其实遵循同一个模板：**先给出一个能精确匹配的文本条件，再说明匹配上之后具体改哪个字段，最后交代「为什么匹配这么窄」**。这种「窄匹配」的设计哲学贯穿全篇——比如 R2 强调「只删这一类行」且要求文案精确匹配（不是模糊包含），R5 强调「压缩成一条」而不是「随便删掉几条」。这背后的原则是：**过滤规则的破坏力和它的匹配范围成正比**，匹配越宽泛，误删真错误的风险越高，所以宁可为每一种已确认的噪声写一条专门的窄规则，也不要写一条「看起来能覆盖更多情况」的宽规则。

### 7.5 那条「升级例外」为什么写得这么绕

这条规则的绕，其实反映了现实世界报错的复杂性：Godot 大多数时候会先打一条 SCRIPT ERROR 说明具体错误，再打一条 `Failed to load script` 包装行说「这个文件没加载成功」。但探针也没有百分之百排除「Godot 只打了包装行、没打正文」这种理论上可能存在但目前没观察到的情况——如果这种情况真的发生，而过滤器又把所有包装行都当噪声删掉，就会导致一个真实存在的错误完全消失，Agent 永远看不到任何提示。

这条「窄例外」就是在两种风险之间找平衡：既不能因为「万一有正文缺失的情况」就把所有包装行都当根因保留（会导致 autoload 假阳性、级联症状全部涌回 reward，回到最初要解决的问题），也不能完全不管这种边界情况（会有一天真的漏检一个错误却毫无察觉）。解决办法是把触发条件卡得极窄：**只有当解析阶段——也就是任何过滤规则介入之前——就已经确定这个文件从头到尾没有任何 SCRIPT ERROR，才允许升级**。这样一来，因为 R2 删除了 SCRIPT ERROR 而导致的「事后变空」不会触发这条例外（因为它在解析阶段是有 SCRIPT ERROR 的，只是后来被过滤规则删掉了），真正「从一开始就没有正文」的情况才会触发。

### 7.10 为什么专门强调「样例 F 的 V2 结果必须仍然输出 pointer」

这条测试断言看起来有点奇怪——V2 已经在检查具体文件了，为什么还要输出 pointer？原因是：**V2 检查的是 `dep_1.gd` 这个文件本身，但 `dep_1.gd` 报的错误内容是「我引用的另一个文件 `root_bad.gd` 加载不了」**，这条报错本身仍然是「指向别处」的性质，并不因为它出现在 V2 的结果里就变成了「关于 `dep_1.gd` 自身的根因」。如果实现的人图省事，觉得「反正已经是单文件检查了，pointer 这个概念应该只在 V1 才有意义」，就会把这条 pointer 错误地升级成根因，或者错误地丢弃——两种处理都会让 Agent 误以为 `dep_1.gd` 有自己的语法问题，而实际上真正需要修的是 `root_bad.gd`。

## 8. `[autoload]` 解析

这一节看起来是最简单的一节（几行文本解析规则），但背后有一个容易被忽略的教训：**不要假设配置文件里的值格式是统一的**。N02 实测发现，插件通过 GUI 启用之后自动写入的 autoload 值用的是 `uid://` 格式，而手写的 autoload 用的是 `res://` 格式——如果解析代码里写了一条隐藏的假设（比如用正则强行要求值必须以 `res://` 开头），会导致插件注册的单例完全无法进入白名单，autoload 过滤规则对这类单例形同虚设。这也是为什么文档专门提醒「不要断言值必须是 res://」——这种提醒往往来自一次真实的踩坑经验，不是凭空多虑。

## 9. 各命令下过滤器的预期行为

这张表本质上是一份「使用说明书」，告诉集成这个过滤器的人：**V1 的结果不能拿来当「项目所有文件的完整错误清单」，V2 看不到 shader，V3 不是查语法错误的主要手段**。如果没有这张表，最常见的误用方式是「反正 V1 也能报错，干脆全靠 V1 就够了」，然后在真实项目上发现大量错误被漏检——因为 V1 的哨兵脚本一旦自己先解析失败，后面深层的问题根本不会被打印出来（这一点在 §2.1「V1 必须可重复」那段注解里也提到过，是同一个现象的两种表现）。

这一节末尾反复出现的「单次 `passed` 不能用在项目级」，和 §4 数据模型注解里讲的道理是同一件事，这里再强调一次是因为这是整份文档里最容易在真实实现中踩坑的一条——**它不是一个「难以理解」的规则，而是一个「容易在写代码的时候手滑忘记」的规则**，所以文档选择反复出现在多个章节，用重复来对抗遗忘。

## 10. 测试矩阵

这份表格与其说是「测试用例列表」，更像是**把整份方案的核心决策一条条转换成可验证的断言**。每一行背后都对应前面某一节的某条规则，读这份表格的一个有效方法是：挑几行你觉得「有点意外」的断言（比如 T-F 要求 `status=CLEAN` 但同时又有 1 条 pointer），回头去 §4/§7.9/§7.10 找对应的解释——如果这份表格里的每一条你都能在正文里找到依据，说明你已经理解了这份方案的核心逻辑；如果有哪一条看着莫名其妙又找不到依据，那可能是文档本身有遗漏，值得提出来讨论。

`T-STOP` 这一条尤其值得注意：它测的不是「过滤器删对了什么」，而是「过滤器有没有老实承认自己不知道」——`status=CLEAN` 但 `untrusted` 非空，意思是「表面干净，但这不代表真的没问题，只是我们看不到而已」。这条测试如果被删掉或者放宽，很容易在未来的某次重构中，把「宣称干净」和「确认干净」这两件事悄悄划上等号。

## 11. 明确不要做的事

这份清单是**整份文档所有「坑」的浓缩索引**。有意思的是，这十七条几乎每一条背后都对应一次具体的探针实验发现（一个真实观察到的现象）或者一次审核发现的实现陷阱，不是凭空想象出来的注意事项。建议把这份清单当成「实现完之后的自查表」——写完代码，逐条对照，看有没有不小心踩中某一条。

后几条（14-17）是审核阶段才加入的，都是同一类问题的不同表现：**代码表面上看起来完成了功能，但在某个特定输入形态下会产生错误的、难以察觉的行为**（用错路径字段、把多命令合并逻辑混进单命令处理、只跑一轮就收工、把跑完收尾门当成完工）。这类问题的共同特点是「正常路径测试能过，但边界场景会静默出错」，所以文档选择把它们写成显式的禁止条款，而不是指望实现者「自然会想到」。

## 12. 与外壳的分界

这一整节存在的目的，是防止一种常见的项目管理问题：**过滤器和外壳（runner）由不同的人实现，或者在不同的时间点实现，如果没有一份清晰的契约，两边很容易在交界处产生「谁负责这个」的分歧或者遗漏**。这张表格的读法是：左列是「外壳承诺会做的事」，右列是「如果外壳没做到，过滤器会表现出什么症状」——**右列本质上是给调试过滤器的人准备的一份排查指南**：如果发现过滤器表现异常，先检查是不是外壳没有遵守左列的某一条承诺，而不是先怀疑过滤器本身的逻辑有 bug。这在实际调试中很有价值，因为过滤器是纯函数、逻辑相对简单，反而外壳涉及进程管理、文件系统状态，出问题的概率更高。

## 13. 建议的文件布局

这一节的实用价值不在于「必须严格照抄这个目录结构」，而在于它体现了整份方案反复强调的「关注点分离」原则在文件粒度上的落地：`parse.py`/`signature.py`/`autoload.py` 各管一件事，`rules/` 下每条规则一个文件，`pipeline.py` 只负责编排顺序、不包含具体规则逻辑，`merge.py` 单独存在（对应前面反复强调的「R8 不属于单次过滤」）。如果实现的时候把这些逻辑都堆进一个几百行的文件，短期看起来省事，但每次要改一条规则时都要在一个大文件里定位，且很容易在改动时不小心影响到不相关的规则——这正是文档里那句「不要揉成一个 800 行 rules.py」想要避免的情况。

## 14. 完成定义

这份清单的作用是**把「做完了」这件事变成可以机器验证的东西，而不是靠主观感觉判断**。八条里前六条几乎都能直接翻译成一次 `pytest` 断言，最后两条（不存在 `exit_code == 0` 的短路、改 role 只用 replace）更像是「代码审查清单」，需要人工检查代码写法而不是运行测试。

值得注意的是，这八条里至少有三条（第 5、6、7 条）是专门针对审核阶段发现的问题设的——也就是说，这份「完成定义」本身也是随着理解的深入不断补充的，它不是一次性写完就不再变的东西。如果未来又发现了新的边界场景，应该继续往这份清单里加条目，而不是让完成标准停留在最初的理解水平上。
